# Phase 4e implementation plan

Begin product changes only after Phase 4d's full PostgreSQL gate is published and
the exploration design review is resolved. Existing user authorization covers this
architecture-aligned work. Use TDD, bounded parallel tasks, independent review and
a frozen final verification run. No live provider calls or external effects.

1. Policy/admin task owns strict opt-in policy parsing, the narrow authenticated
   governance toggle and CLI, atomic audit/revision handling, and focused tests.
   Preserve unrelated governance fields; document in-flight disable semantics.
2. Schema task owns exploration state/grant models, migration 0012, exports and
   schema tests with populated downgrade guards. Agree exact fields first.
3. Store task owns immutable grant/hash validation, scheduling/accounting,
   classification and owned read-only snapshots, with focused PostgreSQL tests.
   Coordinate interfaces before implementation; it must not import runtime/cognition
   or stores/cognition and create a cycle. Existing active work stays frozen.
4. Root owns claim isolation and exact physical limits, preflight/recovery ordering,
   mandatory context integration, no-wake-request enforcement and diagnostics.
   Keep normal cycles and public protocol schemas stable. Runtime start permission
   must serialize with the same lock used by the authenticated toggle.
5. Acceptance/review tasks, once earlier agent slots free, verify fresh-model behavior,
   ordinary priority, failed/abandoned attempt accounting, disable while in flight,
   exact D1 without a model, pause/config deferral and toggle/long-silence limits.
   Review implementations independently of their authors, including classification
   before filtering mutable owner/kind and content-redaction recovery.
6. Resolve findings, run static checks and focused regressions, then freeze source
   for the complete PostgreSQL suite. Record the actual gate, publish reviewed
   commits, and continue toward perception ingestion with the academic architecture.

The grant is optional and internal only. No operational instance is enabled merely
by implementing the feature or running tests; explicit operator policy controls it.

## Proposed shared interfaces for implementation review

- `ExplorationState`: individual primary key, policy version 1,
  `next_eligible_at`, unique nullable `managed_wake_id`, nullable
  `last_terminal_cycle_id`, nullable `last_outcome_event_id`,
  `materialization_pending`, positive `revision`. Cancellation updates the outcome
  event while retaining the most recent real terminal cycle. The event envelope is
  the cadence anchor, including cancellation with no cycle.
- `ExplorationGrant`: wake primary key/FK (grant identity), individual FK/index,
  policy version 1, authorizing governance revision, policy snapshot, `created_at`,
  `not_before_at`, scope `internal`, caps `max_turns=1`,
  `max_attempts_per_turn=2`, `max_seconds=120`, `max_wakes=1`, canonical content hash.
  Hash every immutable field. Mutable wake timing cannot accelerate this grant.
- Keep strict policy parsing and immutable grant validation independent of runtime
  imports. Invalid reserved policy denies new starts but is distinct from absent
  policy (valid disabled). Preserve exact result recovery under both conditions.
- Add a pre-invocation settlement helper used before compilation/model checks and
  rechecked inside `start_invocation`. It can mark previous-process starts abandoned
  and terminalize exhausted/disabled work without creating a new invocation. A
  decided turn is handled first and is never rewritten by this helper.
- Use a detached typed exploration-control snapshot for pure context compilation.
  Its canonical representation binds grant/wake identity and effective stored cycle
  limits. Recovery compares exact type-sensitive canonical content, category, refs
  and unique section presence against durable membership.
